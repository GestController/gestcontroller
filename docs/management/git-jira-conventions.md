# Git, GitHub and Jira Conventions

| | |
|---|---|
| **Project** | GestController |
| **Jira task** | SCRUM-11 · GestC01 - Define conventions for branches, commits, and pull requests |
| **Version** | 0.2 (draft for review) |
| **Date** | November 2026 |
| **Applies to** | Everyone who changes the `gestcontroller` repository (code, infrastructure and documentation) |

## 1. Purpose

These conventions keep the history readable, make every change traceable to a Jira task and reduce mistakes. They are short on purpose: if a rule is hard to follow, we change the rule.

## 2. Principles

1. **One task, one branch, one pull request** (a large task is split into subtasks, each with its own branch).
2. **The Jira key is everywhere:** branch, commit and pull request title. That is what links GitHub with Jira.
3. **Nothing reaches `main` without a reviewed pull request.**
4. **Small changes:** easier to review, easier to revert.
5. **English only:** branches, commits, pull requests, comments and documents.
6. **No secrets in the repository, ever.**

## 3. Names in Jira

| Item | Format | Example |
|---|---|---|
| Sprint | `GestCnn - Name` (two-digit number) | `GestC01 - Scope and management plan` |
| Task title | `GestCnn - Verb + object` | `GestC01 - Draft scope and objectives document` |
| Sprint label | The sprint code | `GestC01` |
| Type label | One of: `documentation`, `management`, `infra`, `backend`, `frontend`, `testing` | `documentation` |
| Key | Generated by Jira, never changed | `SCRUM-9` |

If a task is carried over to the next sprint, update the code in its title and its sprint label.

## 4. Branches

### 4.1 Model
Trunk-based: `main` is the only long-lived branch. All other branches are short-lived and deleted after merging.

### 4.2 Naming
```
SCRUM-<number>-<short-description-in-kebab-case>
```
- Start with the key of the task (or of the subtask, if the work belongs to a subtask).
- Lowercase after the key, words separated by hyphens, no more than about 50 characters.

| Kind of work | Example |
|---|---|
| Documentation | `SCRUM-9-scope-and-objectives` |
| Feature | `SCRUM-21-add-role-endpoint` |
| Infrastructure | `SCRUM-30-terraform-qa-network` |
| Fix | `SCRUM-35-fix-policy-cache-ttl` |

### 4.3 Rules
- Create the branch from an up-to-date `main`.
- One task per branch. If a task needs several pull requests, use the subtask key or add a suffix (`SCRUM-21-add-role-endpoint-part-2`).
- Keep the branch up to date by merging or rebasing `main` before opening the pull request.
- Delete the branch after the pull request is merged.

## 5. Commits

### 5.1 Format
```
SCRUM-<number> <summary in the imperative mood>

<optional body: what and why, wrapped at about 72 characters>
```
- The summary is a short sentence, **60 characters or fewer** after the key, starting with a verb: `add`, `fix`, `update`, `remove`, `refactor`, `rename`, `document`.
- No period at the end.
- The body is optional; use it to explain *why* when it is not obvious.
- One logical change per commit.

| Good | Not good |
|---|---|
| `SCRUM-9 add scope and objectives document` | `updated stuff` |
| `SCRUM-21 add endpoint to create roles` | `SCRUM-21 changes` |
| `SCRUM-30 fix security group rule for ALB` | `fix` |

### 5.2 Working-in-progress commits
Frequent small commits are fine while working on a branch. The pull request is merged with *squash*, so the final history on `main` has one clean commit per task.

## 6. Pull requests

### 6.1 Title
```
SCRUM-<number> <summary>
```
Example: `SCRUM-9 Draft scope and objectives document`. With *squash* merge, the title becomes the commit message on `main`.

### 6.2 Content
Use the pull request template (`.github/pull_request_template.md`). It asks for the Jira key, what changes, why, how it was verified and a checklist.

### 6.3 Size and draft
- Aim for **fewer than 400 changed lines**; split bigger changes.
- Open a **draft** pull request for work that is not ready for review.

### 6.4 Review
- At least **one reviewer who is not the author**.
- Review within **one working day**, so sprints do not stall.
- The reviewer checks: it matches the task and its acceptance criteria, it is understandable, tests and documentation are updated and there are no secrets.
- The author answers every comment (fix it or explain why not).

### 6.5 Merging
- All checks must pass (CI, when it exists).
- Method: **squash and merge**.
- After merging: delete the branch and move the Jira task to **Done**.
- Conflicts are resolved by the author, in their branch.

## 7. Jira status and Git

| Moment | Jira status |
|---|---|
| The task is picked up and the branch is created | In progress |
| The pull request is open and waiting for review | In progress (the pull request shows in the task's *Development* section) |
| The pull request is merged | Done |

## 8. Protecting `main`

Ideal rules, if the plan allows them (branch protection or rulesets): require a pull request, require at least one approval, require passing checks, block force pushes and deletion.

> On a GitHub organization with the free plan, protection rules only apply to **public** repositories. Because this repository is private, these rules are a **team agreement**: nobody pushes directly to `main`, every pull request has a review and checks must pass before merging. This risk is tracked as R-11 in `risk-register.md`.

## 9. Documentation changes

Documentation follows the same flow: branch with the key, pull request, review. When a document is finished, update the status table in `docs/README.md` in the same pull request.

## 10. Versions and tags

- Version tags use `vMAJOR.MINOR.PATCH` (for example `v0.1.0`).
- A tag marks a state that passed QA. The Production tag is created by hand after QA tests pass (see `../devops/ci-cd.md`).

## 11. What is never committed

- Lab credentials, access keys and tokens.
- Private keys (`.pem`, `.key`).
- Terraform state files (`*.tfstate`).
- `.env` files and any file with secrets.

Baseline `.gitignore` (add to the repository from the first commit):
```
# Secrets and credentials
.env
.env.*
*.pem
*.key
credentials

# Terraform
.terraform/
*.tfstate
*.tfstate.*
*.tfvars.secret

# Dependencies and builds
node_modules/
dist/
build/
coverage/

# Editor and system
.DS_Store
.vscode/
.idea/
```

**If a secret is committed by mistake:** treat it as exposed. Revoke or rotate it immediately (for lab credentials, end the session and renew), then remove it from the repository. Deleting the file in a later commit is not enough, because it stays in the history.

## 12. Quick reference

```
# Start a task
git checkout main && git pull
git checkout -b SCRUM-9-scope-and-objectives

# Save work
git add <files>
git commit -m "SCRUM-9 add scope and objectives document"
git push -u origin SCRUM-9-scope-and-objectives

# Keep the branch updated
git fetch origin
git rebase origin/main        # or: git merge origin/main
```
